# /test-driven-development — 红绿重构

可选线索：{{feature_description}}。未替换表示未提供；完整需求以原对话和指定文件为准，参数不保证保留长自然语言。

使用项目已有测试框架和约定。保留已有实现及用户改动；不能因为代码先于测试存在，就删除实现重做。为既有代码补测试有价值，但不能伪称已完成测试先行的过程。

## RED：建立行为约束

1. 明确输入、输出、副作用和用户限制，按风险拆分可独立验证的行为，不规定固定切片数量。
2. 编写能区分正确和错误行为的测试，覆盖本次问题所需的正常、边界或异常路径；避免只复述实现细节。
3. 运行并检查真实失败原因。缺少目标接口可以是预期失败；依赖缺失、无关编译错误或测试自身错误属于阻断条件，不是行为缺陷的证据。
4. 测试直接通过时检查既有实现是否已满足契约。可保留有意义的回归测试，不为制造红灯破坏代码或改错断言。

## GREEN：最小正确实现

- 对尚未满足的契约实施必要修改，不顺带重构或添加未来扩展点。
- 实现应满足真实需求，不能为了单个测试硬编码错误行为，也不能明知必要边界存在却以“尚未测试”为由忽略。
- 重跑目标测试，并按影响范围运行相关回归。每个小步骤不固定要求全量测试；新失败或风险扩大时增加验证。
- 不为变绿而削弱断言。若测试契约确有错误，先说明证据，再按正确需求修正。

## REFACTOR：有收益才调整

测试稳定后，仅做当前任务授权且有明确收益的结构改进，保持行为不变。验证失败时定位差异；需要撤销时只处理本次自己的改动，不整库回退，不撤销用户已有工作。

## 交付

报告实际修改、测试所覆盖的契约、已运行命令与结果、既有失败和未验证部分。覆盖率采用项目已有标准并如实记录，不杜撰统一的 80% 门槛，也不把测试通过当作全部行为正确的证明。没有可用测试基础时说明缺项；引入新依赖或扩大任务范围须符合用户授权。
