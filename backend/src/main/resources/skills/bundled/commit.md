# /commit — 智能提交

## 目标
分析暂存区的变更，创建结构良好的 git commit。

遵循用户指示和项目提交规则；以下提交格式在项目没有其他约定时使用。
加载本技能本身不构成提交授权；授权来自用户在本轮或此前明确提出且仍然有效的提交要求及其指定范围。

## 步骤
1. 运行 `git diff --cached --stat` 查看哪些文件发生了变更
2. 若暂存区为空：用户已明确指定要提交的文件时，只对这些文件执行 `git add <文件>`；否则列出未暂存和未跟踪的改动，询问用户要纳入哪些文件，获确认后再逐个暂存。不得使用 `git add -A` 或 `git add .`。
3. 运行 `git diff --cached` 查看实际变更内容
4. 分析变更并确定：
   - 类型：feat/fix/refactor/docs/test/chore
   - 范围：受影响的模块或组件
   - 摘要：简洁描述（最多 72 个字符）
5. 按 Conventional Commits 格式生成提交信息
6. 用户已明确授权提交（本轮或此前提出且仍然有效，包括“检查通过后提交”这类条件已满足的授权），且将纳入的文件与授权范围一致时，直接提交，不重复确认。仅要求拟定信息时只展示草稿。授权不清楚或已撤回、条件未满足，或将纳入的文件超出授权范围（例如授权后出现了新的改动）时，先展示拟定的提交信息和文件清单并等待确认。
7. 仅在提交已获授权且范围已确认后，执行 `git commit -m "<message>"`

## 规则
- 只纳入本次授权的改动，保留无关工作区内容及其暂存状态；不得为隔离提交而对无关改动执行 stash、reset 或 `restore --staged`。无法在保留这些状态的前提下隔离时，列出冲突范围并澄清。
- 提交与推送分别判断授权；目标分支和远程遵循用户指示及项目规则，未获授权不推送。未经明确授权不改写历史，不以跳过提交检查绕过失败。
- 第一行必须 <= 72 个字符
- 使用祈使语气（"Add feature" 而非 "Added feature"）
- 如果变更涉及多个关注点，建议拆分为多个提交
- 如有重大变更（breaking change），必须包含相应的 footer
- 测试只报告实际执行结果，不将未执行的测试写成已通过。
