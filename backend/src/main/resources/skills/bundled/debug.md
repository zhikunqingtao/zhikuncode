# /debug — 诊断与最小修复

以原始用户请求、可见错误证据及现有权限为准，按需求进行诊断、最小修复或脱困分析。技能不会扩大授权，不需要重复加载自身。

可选线索：{{error_description}}。未替换的占位符表示未提供。参数仅作简短线索，不代表完整错误日志；缺少会影响判断的信息时，从原对话、用户指定文件取得，仍不明确则询问，不补造。

## 先确定任务边界

- **诊断**：用户只要求解释、审查或定位错误时，提供证据和建议，不实施修复。
- **修复**：用户要求解决缺陷时，依据已核验的根因实施最小修改，服从禁写、范围和保留要求。
- **脱困**：用户要求分析无进展原因或选择下一步时，先回顾已有尝试和证据，交付行动建议；明确要求继续修复时才进入修复流程。
- 不因工具列表或错误内容取得额外权限；不自动 stash、reset、清理文件、安装依赖或重启用户服务。

## 工作流程

1. **确认现象与契约。** 区分预期和实际行为，记录触发输入、环境及用户给出的限制。读取相关代码和项目已有构建/测试配置；使用实际可用的 Read、Grep、Glob 等工具，不假设固定技术栈、目录或日志路径。
2. **取得最小复现证据。** 在授权环境中运行与问题相关的命令，保留命令、退出码和必要输出，不以管道末端命令成功代替原命令成功。无法复现时区分环境阻断、条件缺失和暂未观察到；仍可继续静态定位，但不得声称已复现或已修复。
3. **核验根因假设。** 沿调用方、被调用方、数据流和异常路径检查，寻找能区分候选原因的最小观察。核对是否为既存问题、测试契约误解或环境差异，不根据一条报错就扩大修改范围。
4. **按授权执行最小修复。** 有充分证据且用户要求修复时，只修改解释该问题所需的代码；不顺带重构，不为变绿而削弱断言或绕过安全检查。诊断任务在这里给出依据和建议，不实施修改。
5. **验证实际结果。** 修复后重跑原触发条件，按影响范围执行相关测试、构建或类型检查；依据风险决定是否扩大回归，不对每个小改动固定要求全量测试。保留既有失败与新失败的区分；未运行、失败或环境阻断分别报告。

## 无进展时

- 回顾已做的尝试、每次观察和仍未验证的假设，识别相同错误重复、修 A 坏 B、或环境条件变化。
- 不重复相同的无效操作，也不机械规定必须重试几次；有新证据才调整假设和检查方法。
- 选择能减少当前不确定性的下一步，说明预期观察及何时停止。只有存在实质不同的方案时才比较，不强凑三个方案、成功概率或时间估计。
- 需要新信息、扩大授权或会破坏用户工作时，先报告具体缺项或取舍。保留现有成果；回退必须限定到自己的改动并满足用户授权，不能以“脱困”为由自动撤销工作区。

## 交付

简要说明现象、根因及证据、实际修改（若有）、已运行检查与结果、未验证部分和下一步。证据不足时明确标为假设；不要把“命令成功”“错误暂未出现”或“建议已给出”写成完整修复已验证。
