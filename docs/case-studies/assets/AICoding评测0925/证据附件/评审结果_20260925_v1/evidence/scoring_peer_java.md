## 3. 权重、严重度与建议的共同标尺

- D1总权32中，真实请求挂起5、会话/许可恢复4、取消终态3的排序有可解释的影响依据，不能因仅某报告发现而删掉高权机会。建议给每个权重补一句影响依据：请求可越过预算挂起、异常后阻塞后续会话、资源已退出但终态误判。G07八份均漏得0并不偏向某报告；只是公开机会集不完全时的共同覆盖分母。
- G02完整发现应要求追到session注册/后续请求阻断；只看到capacity保留给0.5合理。G03应要求失败close latch、TTL不重新RPC、祖先确认恢复中至少有机制闭环；只说“不释放容量”给0.5合理。平台剩余限制和deadline竞争既有部分保持低权重合理；不可把修复未覆盖均等同新回归。
- “无完成期自动重试”“rootdead仍必然永远不确认”“只能JVM/进程重启”“退出0变工具失败即P1”应对八份按同样条件扣因果/严重度；已承认条件的报告不能再按无限或无条件后果扣。共享deadline旧有、首次hook前门控新增、Docker hook自身旧有早退必须保持三层区别，E01 S1与E02 P2-1均属部分支持。
- D6对E06/E08的 Optional[Request]错误建议均给2/4，方向一致，且有真实路由注册反证；应保留扣分。强制释放未知资源的lease/capacity/registry、rootdead即当整树确认、恢复任意LRU也都有具体安全损害，应扣建议项。仅建议有归属的reaper、确认后升级关闭、真正过期且无在途操作的回收，不应被同等扣。建议将“错误导致新功能破坏/失去归属”与“建议缺实现细节”区分为明确锚点，避免同类危险建议在2与2.5间只因文字长短浮动。
- E06:513确实指出真实Request轮询测试缺口，因此D5测试项理由成立；不能因它没发现具体CancelScope根因就反称报告完全没提真实Request。D1评发现，D5评具体覆盖审查，二者允许不同得分。
