# E01–E08 修复建议与发布结论的独立审计

范围：只审建议的对症程度、资源归属安全、Java 归因/严重度与发布结论；不排名、不修改主审评分。`E01:148–151` 等均指 `inputs/E01.md` 的报告行号。依据为本目录 `ground_truth_java.md`（J1–J6）、其确定性探针，以及 `../python/ground_truth_python.md`（GT-PY-01～04）和目标/父提交源码。建议本身未实施。

共同约束：**超时或已发取消不等于资源退出；根进程退出不等于整树退出；SDK close 异常后的第二次无操作返回不等于清理成功。** 如果要把 Run 租约/正常执行槽与残留资源分离，必须先原子转交给可达的独立监督者，继续追踪真实存活容量、迟到分配和 PID/代际身份，并避免旧任务继续影响新同会话工作。TTL 可以触发重试、告警或已授权的上级资源回收，不能单凭到期删除归属。每份最多八条。

## E01

1. **启动窗口建议一半对症、一半危险**（E01:148–151、299–300）。有界等待 processRef、显式 launch-pending、quiescence 后重取摘要可修 J1；“未启动即 confirmed”或直接剔除 unconfirmed 不能证明启动已取消。必须等待启动事务结束/失败并释放 lease；若总 deadline 到仍悬而未决，应保持 pending/unconfirmed。风险主要是终态误判，P0 优先级标签过强，不能从一次 58ms 采样推算 Linux 的典型时延（E01:144）。
2. **reaper 可采纳，30s 后释放许可不可直接采纳**（E01:178–184、303–304）。报告 E01:182 的“正常结束不会任何重试”遗漏 RunTracker.completeRun 的完成期重试；真正缺口是该次及 coordinator 重试仍失败、进入终态后资源迟恢复。保留“成功即 releaseRetained”的 reaper 与指标；TTL 自动返还 capacity 需独立残留资源配额，否则实际活进程可无限堆积。
3. **inspection 降级须保留未知范围**（E01:18、115–116、207–217）。将 descendants 异常隔离，让 Linux 组扫描继续是可研究的改善；但 groupScanDone 只证明该组，不能覆盖可能已脱离组的 Chromium 后代。未知范围不能只改成告警后返回整树成功。其“异常一次便永不确认”被自身死根探针与本轮16ms反例否定；持续失败条件需明列，不宜作为通用主路径故障。
4. **行为文档合理，exit0直接降为成功是产品契约改动**（E01:165–174、221–223）。命令主体退出码与资源清理结果可以分字段表达，文案可明确已执行；但不能因 root exit0 就让上层认为副作用已终止。优先引导长期服务使用 is_background，保留未确认结构化状态与真实归属。E01:169 的 shell 更新“副作用”无实际 CWD/env 丢失，方法只有日志。
5. **过期会话回收可采纳，未完成分配 TTL 不能丢账**（E01:198–203、306）。仅对真正过期、无在途使用/owner、身份未替换的会话尝试 close，确认后才能释放配额；普通交互会话 owner_task 也为 None，不能把“无 owner”单独等同可驱逐。`_creating/_unclosed_contexts` TTL 必须保留 late allocation/失败 close 的责任，不能直接 pop。
6. **deadline 对照需纠正一处细节**（E01:342）。共享2s预算的确既有，但 parent cleanup 首次会调用 hook，HEAD 才在首次调用前检查 remaining。实际 Docker ensureRemoved 自身也检查过期 deadline，所以 Docker 有效 rm 被跳过不是全新的现象。该条宜“部分支持”，不应把旧首次调用路径描述反了。
7. **发布与闭环结论应限域**（E01:6、26、267–284）。常规 Linux 命令保真可保留；“R1唯一正确性问题”“启动窗口内失控已解决”“前端无改动即无影响”过宽：J2迟恢复锁定和真实 ASGI watcher 问题也影响用户。E01:343 已准确承认非Linux旧限制；建议把发布结论写为测试环境/路径通过，需补取消终态、终态后恢复、真实Request集成门禁。

## E02

1. **P1-1 的核心 CWD/env 因果不成立**（E02:25、79–83、146、180）。恢复 updateStateFromSnapshot 只恢复 debug 日志；shell 已原子写 cwd，env 本就不跨调用保存。保留清理文案、分类元数据/输出一致性建议；不能以该空操作支撑 P1 或预测模型必然重复执行。exit0+cleanup未确认报失败是既有安全目标的前台扩展，不自动构成缺陷。
2. **容量链路修正是有效进步，TTL 表述仍需条件**（E02:85–91、210）。明确完成期重试比“没有任何重试”准确。后台重试及无取消后恢复测试对症；“最多N次/老化后回收许可”必须以确认退出或完成安全归属转移为前提，不能只是次数/时间到达。建议按条件性P2描述，若统一评分标准对会话锁定定P1，必须保留该故障前提。
3. **hook 预算建议有用，新增归属不能一概而论**（E02:93–96、178）。共享deadline本来就存在；HEAD首次 hook 前 remaining gate 新增，真实 Docker hook 自身旧有同样预算检查。分配独立 hook 子预算可采纳，但需预先设计整体取消上限/并发清理，不能简单每层再加2秒，使连续取消或shutdown总预算失控。
4. **能力不可用时“快照确认”会重引入漏清理**（E02:109–112、181）。记录能力错误、缺失依赖自检是合理建议；未知 descendants 仅靠 known为空不能证明整树空。应输出确认等级/范围或失败原因，继续保留归属，而不是在公共 terminationConfirmed 上伪装完整成功。不是每次暂时读取异常都会持续失败。
5. **非Linux仅取消时才快照不安全**（E02:132、185）。目前等待期间采样至少能在父进程还活时留住部分后代；只到取消/超时才采样会错过已自然退出的父进程。降频是性能/漏发现概率的取舍，应先用长短命父子对照量化，或增加稳定平台归属机制，不宜作为无风险P3优化。
6. **清理总超时需避免取消唯一资源收尾者**（E02:135）。`asyncio.wait_for` 超时默认取消被等任务，而SDK close/late allocation恰有不能丢所有者的约束，也可能吞取消导致 wait_for 不按时返回。应对保留的任务使用有界等待，返回后由监督者继续持有，配套停机升级；不能仅加wait_for即称整体有界。
7. **Python FAILED 与 DevServer 运维建议总体可采纳**（E02:119–122、130）。保留旧processRef并提供可观测、受控restart/reaper是合理方向；重启要重新确认旧代，不可强清引用绕过防重启门控。“永久不可用”限于缺少可达恢复入口，并非每次start/restart必然失败，短暂检查故障可恢复。
8. **放行结论超出静态证据**（E02:16、20、191–197、204–205）。报告明确未实跑，不能由“未发现P0”推导“可安全保留main/正常路径不变”。建议的Linux冒烟有价值，但20个普通残留清理成功不能覆盖J1/J2与ASGI故障；还要补确定性取消窗口、终态后迟恢复、真实Request门禁。成功Bash ToolResult也未必直接暴露terminationConfirmed键，冒烟应取runner结果或观测事件。

## E03

1. **强删注册/提前释放lease不是安全最小修复**（E03:153–157、320、336）。reaper在成功后释放可采纳；unregister超时就删注册、register遇“已终态”就清理放行，都可能让仍写同一工作区的旧任务和新Run并行。若采用“Run归属转服务归属”，须有原子转交、残留容量计费、可达取消、session副作用隔离与迟到回调身份校验，不能只删map/close lease。
2. **永久锁死的条件与恢复入口被说得过满**（E03:95–105、144–157、233–237）。hook永远false的探针证明“持续无法清理时不放行”，未单独证明故障恢复后不回收。RunTracker有一次完成期自动重试，直接runner取消在资源恢复后可释放；应按J2写成有限重试失败、终态后迟恢复缺自动驱动。P1可讨论，但“一次未确认、不可逆、只能重启”过强。
3. **rootdead+known空的建议会破坏修复目标**（E03:123–129、321）。保留不确定不是错误确认条件过严；已重父化/脱离组的未知子进程正是本次要治理的对象。能力不可用需要明确不完整确认等级，不能复用完整terminationConfirmed。16ms反例也说明并非所有descendants异常都+4秒/永久失败。
4. **CWD建议无效；沙箱分支归属错**（E03:168–174、325）。updateStateFromSnapshot无状态写入，cd快照由shell自身写好，不需“按exit码回写”；export环境不持久化。E03:172称沙箱同形分支“同样新增”不实，parent已有。明确主体退出与清理结果的文案可保留。
5. **“Python做法有界自愈”的类比不能支撑Java最终强制释放**（E03:233–237、336）。Python TTL复查异常完成的同一close task，不发新RPC；真实SDK latch禁止“删失败task再试到成功”。只有pending晚成功或已确认browser/driver祖先关闭才能释放。应保留可观测+升级清理建议，删去“TTL保证最终释放”的承诺。
6. **扫描/缺依赖降级须保住真实归属**（E03:133、138、334）。只扫一次后仅known集合可能漏掉终止期间新生/新发现后代；Linux缺setsid自动回退直启会默默削弱已约定的重父化保证。可采纳退避、自检、错误指引；降级需显式能力等级及契约选择，并验证不引入原漏清理。
7. **容量先驱逐过期会话可采纳，仍需确认close**（E03:206–207、326）。is_expired且owner为空比恢复任意LRU更合理；须重新校验活跃/closing/身份、锁外关闭后确认结果，再原子预留新容量。不可把SDK失败对象TTL老化后当成已释放。
8. **发布“常规正常”可限域保留，勿称全链路无正确性问题**（E03:53、299–312、370）。Linux探针证明其覆盖的保真/清理组合，不覆盖Run窗口、全部正常浏览器/ASGI；E03遗漏J1且把F2普遍化。可以建议无需整体回滚并列具体门禁，不能用测试总数或F2推断支撑全面安全/全面受限主机故障。

## E04

1. **“主要不在正确性/两侧全绿即可合并”需收窄**（E04:16、22、53–62、155–158）。测试通过说明覆盖路径通过，不能排除已证明的J1终态误判和真实ASGI watcher挂起。发布建议可以接受fail-safe语义，但须把这两项列为验证/修复条件，而不是仅产品确认三项取舍。
2. **S1把空日志方法当状态丢失，并把受限mac全命令失败外推**（E04:68、140）。两项均不成立：CWD文件已原子更新，env不持久化；枚举异常在root死后可以下一轮恢复。文案说明主体已退出值得采纳，S1的P1不应由这些错误因果支撑。
3. **容量告警有用，“无限增长”与组件归属混淆**（E04:69、96、141）。Java active正常受16槽限制，浏览器会话/创建/未关闭配额默认10；`_resource_close_tasks`属Python而非ManagedProcessRunner。不能直接断言所有容器无界增长。新增保留上限不能丢弃仍活资源，应以准入拒绝、监督重试、确认后的释放维持真实上限。
4. **容量拒绝不是应恢复的无条件P1缺陷**（E04:70、142）。拒绝新会话保护已有用户/资源上限，报告承认安全取舍是合理的；错误码、等待/显式关闭指引可采纳。要恢复回收，只能真正过期且无活跃占用的会话、确认close后腾位，不能为了第11个请求让旧用户无声丢会话。
5. **创建waiter超时不能取消唯一分配所有者**（E04:97）。给普通等待者自身超时/稳定错误码可行；不能通过取消allocation、清reservation让后来的new_context无人接收。应与独立allocation/rollback生命周期保留配额配套，并测“请求已返回后late allocation被关闭”。
6. **SDK私有API升级测试、日志、真实浏览器CI可保留**（E04:98、113–124、157）。这些可行动且不削弱所有权。语义明确的未确认不是“npm已装好故应成功”；若要改变工具状态，仍需独立字段保留资源风险。缺setsid只是非默认部署前提（E04:75、143），不宜与官方镜像当前启动阻断混算。

## E05

1. **J1建议中quiescence后复查最对症**（E05:91–95、333）。显式pending、同deadline有界等待、重新获取summary均合理；“已接管”应独立于confirmed，不得尚未阻止执行就计入已清理。latch控制启动窗口测试比固定sleep可靠。新回归结论有独立A/B支持，但“Linux更长、命中概率不低”（89）无基准不能当严重度证据。
2. **容量语义需降温，expired-only建议有条件可取**（E05:97–116、335）。从驱逐改拒绝是有意保护，不等同资源泄漏或所有浏览器操作失效（已有session仍可用）。须将裸错误码/恢复指引与配额保护分别评价；普通会话owner为空不代表没人使用，必须真正过期/无在途动作并确认关闭才可腾配额。
3. **解析“显式&”作为豁免会打开未监督后门**（E05:132–137）。语法检测既不等价长期服务意图，也不能赋予session生命周期；豁免后可能重引入正常命令遗留子进程。推荐文档引导is_background，或把明确后台意图迁移到既有session-owned启动API，配额和取消责任必须同步转交。不能简单恢复不清理。
4. **rootdead即可确认的降级建议不可采纳**（E05:153–161、334）。报告“root被杀后仍无法确认”的一般因果被J6反例否定；known集合只包含已发现对象，空集合不是不存在未知子进程。EnumerationStatus可作诊断，但UNAVAILABLE不得自动提升为完整成功。测试能力检测可以用于不支持的平台，不能把应有能力的真实回归全部assume跳过。
5. **升级browser回收比重试失败close正确，但需防误伤活跃会话**（E05:163–179）。保留失败SDK task符合latch安全。browser.close/driver shutdown+startup可恢复，故“只能重启整个进程”不准确；升级要先停止新准入、取消/交接活跃owners、确认祖先释放、处理迟到allocation，再新建一代，且不能因一context异常直接无声杀掉其他用户浏览器。
6. **OwnedProcess.destroy改为整树终止不是无风险小修**（E05:233）。当前生产调用均显式terminate，未证实直接destroy调用导致回归。可先补Javadoc；若改变标准Process方法的阻塞/优雅顺序语义，需明确deadline、并发single-flight与兼容测试，不能把可能阻塞数秒的整树终止悄悄塞进destroy。
7. **发布谨慎结论合理，“唯一正确性缺陷”应撤回**（E05:27、333）。新取消终态缺陷足以要求验证；但J2的终态后迟恢复、真实Request集成风险也存在。正常Linux回收在报告没执行，不宜用macOS的未捕获子进程推出“仅Linux能触发任何子进程回收”（134）；非Linux已采样的后代也能清理。

## E06

1. **reaper正确，流关闭归还capacity/强删execution危险**（E06:178–184、557）。181明确“成功后释放”可采纳；182流关闭不能证明子进程或沙箱退出，183强删注册可能让旧任务与新Run同时影响同会话。须按共同约束做真实所有权转交/隔离。报告遗漏完成期自动重试，“无任何自动回收/任一次即永久锁”应改为有限重试失败后缺恢复驱动。
2. **H2已作重要自我修正，但建议仍抹去未知范围**（E06:38、188–216、558）。213承认root死后恢复，与独立反例一致，应同步修正摘要/标题的每条+4s暗示。known+isAlive不能证明未知后代已退出；把inspected移成纯告警会重引入虚假成功。优先隔离可用发现手段、记录确认范围，不能直接恢复旧弱保证并保持相同confirmed含义。
3. **前台语义文档可采纳，恢复仅取消清理或exit0一律告警需谨慎**（E06:238–243、559）。前台清理是本次核心目标；回退会复活已证Linux孤儿泄漏。允许产品改变工具展示，但cleanupUnknown必须仍可阻止错误quiescence/容量释放；不能用主体exit0替代完整资源终止。将预期安全收紧列P1“缺陷”过强。
4. **metadata与CWD核验较准确，重算枚举字段仍不够**（E06:274–285、571）。283正确排除CWD误报，282的通用truncated OR修复直接对症。descendantTrackingUnavailable应来自清理时记录的失败/能力状态；末尾再调用descendants仍测不到历史/proc失败。此字段探测旧已存在，新增未确认分支只是暴露它，不应与新的truncated遗漏混算。
5. **SDK latch判断正确，恢复边界仍应纠正**（E06:294–300、564）。不得删除failed task后重试close来声称成功；升级browser/driver关闭再重新startup是对症方向。296“进程重启前不会恢复”过强，独立Python探针已证明同进程shutdown/startup在祖先确认后恢复。每次close异常也不证明真实context必然仍活，只能证明未确认；保留是正确安全记账。
6. **DevServer重试与rootdead及时TERM合理，需限定身份和恢复条件**（E06:268–270、324–329、563–566）。只能重试本launcher持有的同一handle，不能只按端口PID杀任意服务；动态端口需同步baseUrl/安全策略，并保持旧资源归属。root死后缩短10秒等待可讨论；“同一停止重试必然失败、快速放弃更好”（325、566）不成立，暂时权限/检查/driver故障可能恢复，不宜删掉合法重试。
7. **Optional[Request]建议会引入新的路由注册失败**（E06:368）。锁定FastAPI中Request是特殊注入类型，直接Optional[Request]会被当成普通Pydantic字段并报FastAPIError；现有Request=None能注册且真实注入。主审锁定venv的注解A/B见 `../root/probe_optional_request.py:1–14`、`../root/optional_request.log:1–2`。应保留Request注解或将无Request的直接单测另走helper，不可为静态告警改坏框架契约。
8. **“成功路径无回归/契约闭环”发布结论需收窄**（E06:33、63、383–395、549）。Java正向保真与SDK latch测试可保留，但报告漏掉J1真实终态回归与真实ASGI Request路径。保留发布前处理恢复通道/观测的建议，同时增加这些具体门禁；不能从mock/直接route测试推导真实HTTP取消闭环成立。

## E07

1. **恢复LRU不能只过滤journey owner**（E07:45–69、259）。普通交互会话owner_task也是None，仍可能有人使用/保留登录态；原LRU静默驱逐正是被去除的破坏行为。容量拒绝本身是有意保护，P1“确定性缺陷”过强。仅真正过期、无在途操作且close确认的回收可采纳，或明示产品允许的淘汰策略。
2. **非Linux缺口实证成立，但不应列为新增P1回归**（E07:15、21、73–101、260）。parent更弱，同类孤儿已存在；本轮mac/Linux对照支持“修复未覆盖”的结论。confirmationLevel是真诚方向；仅设置descendantTrackingUnavailable=true仍需定义与true confirmation的关系，不宜一边完整成功一边警告。
3. **直接复用BackgroundProcessGroup并不自动继承新身份安全**（E07:101、260）。该实现保存PGID后raw group signal，不具OwnedProcess相同startTicks双读校验；且默认丢弃输出。若用作前台，要重新证明PID/PGID复用、shell提前退出、取消启动窗口、输出/环境保真与平台ps能力。不能称一套现成POSIX机制可无缝替换。
4. **最终强制回收必须区分杀资源与删记录**（E07:109–114、262）。后台重试/运维入口可采纳；次数用尽即返还许可或删lease不安全。“强制回收”仅在真实资源已强杀并确认、或独立监督者接手且继续计费/隔离后成立。报告引用RunTracker但仍漏掉其完成期自动重试，需收窄“无任何自动重试”。
5. **CWD/env陈旧及shellStateStale建议应删除**（E07:173–175、264）。状态由shell原子写回，updateStateFromSnapshot只有日志，env不跨调用保存；增加shellStateStale=true会制造新的错误诊断。保留主体退出码与清理结果分层文案即可。
6. **性能退避是折中，不是等价优化**（E07:135–148、263）。macOS采样降频可能更易错失短命父进程；仅known增量检查可能漏新派生成员。应量化CPU与漏发现、最长取消时延之间的界限，并保留周期全量/稳定归属机制。一次4秒探针比值不能外推全部任务吞吐退化25–40倍。
7. **恢复浏览器不能靠反复failed close或简单释放配额**（E07:66、259）。成功的browser/driver ancestor关闭后同进程可以startup，无需总是重启Python；失败latch不能重试假成功。升级须协调其他会话与迟到allocation；将资源配额和逻辑会话上限分离也必须计入仍占用的真实context。
8. **谨慎发布态度可保留，发布阻断理由须换成已证新缺陷**（E07:24、257–266、276–278）。真实浏览器CI、重父化测试、同步原语合理；不能主要以“容量拒绝必须恢复LRU”和非Linux旧缺口支撑两项新增P1。未跑Linux/完整浏览器必须继续明确边界，同时纳入J1/J2及真实Request链路。

## E08

1. **watcher无界join是有效缺陷，但“100%/阻断级”需限定触发**（E08:17–20、59、103–140、328–333）。独立真实HTTP探针确认立即容量拒绝可吞取消、超过工作deadline仍挂起；正常未满容量成功对照返回200。报告delay=0 mock同步完成不能证明真实浏览器所有快速截图都会触发。建议条件性P2，强调请求/资源可能累积，不直接外推全服务P0或所有deadline必挂。
2. **有界等待只能修请求时延，不能放弃仍活watcher的所有权**（E08:142–146、286–287）。`asyncio.wait`比无界gather好，但超时后单纯放弃会保留轮询task泄漏。应设计明确stop event/可取消且单一owner的receive循环，返回后保留监督直到task排空；测试须覆盖真实生产中间件、立即容量拒绝、成功、deadline与disconnect，断言任务数/资源也收敛。
3. **移除watcher并依赖ASGI自动取消不等价**（E08:143–145）。Uvicorn不保证客户端断开就自动取消应用任务；只留120s deadline会退化提前离开即停止的需求。若产品明确接受该降级可作为临时缓解，需说明浏览器动作可能继续到完成/期限。原始request.receive方案也需避免多reader争抢body/disconnect，并验证中间件栈。
4. **Optional[Request]是会制造启动阻断的错误建议**（E08:187–189、278、292）。与E06同因：FastAPI特殊Request注入不可直接包Optional；主审注解A/B（`../root/probe_optional_request.py:1–14`、`../root/optional_request.log:1–2`）确认当前形式注册成功、Optional形式报FastAPIError。不是无功能影响的类型整理。使用非默认Request参数（调整参数顺序/测试helper）或保留现声明，需真实route注册测试。
5. **前台只在超时/取消清理的建议会复活正常退出孤儿漏清理**（E08:152–165、288）。文案区分主体完成/清理未确认合理；不应为了保持exit0即成功而直接恢复旧清理条件。E08只说跳过update，没有明确声称CWD丢失，仍应指出该方法仅日志，不应被算为功能影响。setsid逃逸者若从未被发现反而可能被假确认为成功，不能一概列作terminationConfirmed=false触发例。
6. **容量恢复指引与非Linux旧问题归属较准确**（E08:167–185、289）。不要求恢复任意LRU、承认fail-safe与非Linux非回归可保留；容量错误应明确映射，祖先级恢复需确认关闭、协调活跃会话，不能删除failed close task来重试SDK latch。当前报告未提出这种危险重试，应避免误扣到它。
7. **Java“基本安全”发布结论依据不足**（E08:18、330）。全套测试通过不能覆盖J1启动窗口和J2终态迟恢复；两个新回归已有独立确定性证据。可以说覆盖的常规命令路径通过，不能把Java端概括无回归。E08:205–206仅“文件未改+单测仍失败”也不足单独证明既有，应有parent同参数对照。
8. **测试覆盖措辞与发布动作需精确**（E08:19、137–140、146、287）。报告自己138承认fake Request断连测试，因此“没有一条传入http_request”字面过强，准确说缺真实Request/CancelScope/生产middleware集成。新增真实ASGI/loopback测试、确定性Event同步、失败现场输出保留都是可执行建议；建议无需全面回滚但补齐新缺陷验证，不能仅修watcher即视其他生命周期全部闭环。
