# 评分草案同侪复核：Python主张与E08

复核对象为当前 `evaluation_data.json` 与 `build_evaluation.py`，以及其引用的E02/E05/E06/E08相关原文；没有修改主审文件，没有新增实验。以下意见不以现有名次为目标。草案把发现、准确性、归因、证据分开是合理方向，但目前不宜凭计算后1—2分差声称质量名次稳定。

## 必须修改的事项

### 1. G08给E08完整发现信用是正确的；E02半分偏宽

G08明确命名为“真实Request CancelScope吞watcher取消，finally无界gather可挂起”。E08识别了具体SDK机制、受害task、无界join和HTTP后果；独立ASGI/Uvicorn探针确认实际可达，所以 `E08=1` 必须保留。原脚本未提交不消除已经确认的发现，不能因此改成“未证实”或仅半分。

E02 P3-9仅称gather无总时限并用“cleanup_timeout多资源串行”解释超出130s。在当前Journey单session路径，这个解释没有建立实际可达链，更未识别watcher的取消被吞。按草案“去重机制、不是关键词命中”的口径，它不应取得**具体机制一半**信用。当前0.5使E02从该项获得 `30×5×0.5/32 = 2.34375` 总分，已超过数个相邻排名差。

**建议具体修改：G08 E02从0.5改0；保留E02-F14=部分支持以及D5中对无界等待的审查警觉。** 若主审希望对“识别准确位置和后果”另给信用，需明示一个不同的、低权重结构性预算观察项，或统一所有机会的观察/机制/触发/影响分层标准，不能用高权重具体根因的0.5代替。不要为了平衡名次调整E08的其他分数。

### 2. E08的技术事实与证据保管问题必须分离

E08-F02理由目前以“原脚本缺失”开头。这是D4可复现性事实，不是D2技术反证。应删去这部分作为D2半分的依据，并明确剩余裁决只针对“模拟成功快路径能否代表实际实现”的推断。

合理边界如下：

- 原脚本缺失意味着不能认证报告原5/5测试历史及其完整控制条件；不意味着没运行、更不意味着造假。
- 报告模拟 `_create_context_for_journey` 无await立即返回，能够演示路由取消机制；实际成功创建经过 `create_task + shield`，因此不能凭这组模拟直接量化正常单步截图的发生率。
- 独立容量拒绝路径在第一个driver await之前返回异常，补足了真实生产代码的可达性。它支持E08的**根因和后果**，不证明E08所有示例触发、频率或原测试次数。
- 原报告本文已说“特定时序”“正常多秒通常安全”，不是无条件声称所有Journey挂死。扣分必须针对未证实示例外推，不能按全局必挂的稻草人处罚。

D4给其未留原脚本的复核成本限制是合理的；D6也可以评价建议质量（Optional注解确有实害），但不应再仅因为相同脚本缺失做第三次笼统扣分。

### 3. D2事实族拆分/合并不统一，须先统一再重算

草案声称按“重要去重事实族”计分，但实际粒度影响很大：

- E08一个3.1问题拆为“核心机制”weight3、“成功快路径归因”weight3、“测试参数摘要”weight2；该问题合计8/17分母。一个正确且重要的发现，因此同时承受与核心等权的触发外推扣分，以及相当高的措辞矛盾扣分。
- E06的H13c/d/e/f四个低重要度观察（标签双义、短UUID、总预算分析、扫描开销）各weight1且全对，形成4个正确单位，稀释其重要因果错误。
- E01的C1/C2/C4/C5四个正确契约却全部合成一个weight1；E02也合并部分低重要度事实。长报告能否稀释错误，因作者被如何切分而不同。

这不是要求把所有报告强制同分母；D2本来应评“它实际提出的主张有多准”，遗漏由D1负责。问题是同一重要度和同类主张必须用一致去重规则。

**建议最小可执行修订：**

1. 每个主要问题族先赋统一总权重，再在其内部拆观察、机制、触发、后果；不要把同一P1标题的weight3复制给该问题每个子句。
2. E08核心机制保留weight3/full；触发外推至多weight1/partial，或只在D3校准维度体现；“全部无http_request”字面确错，但正文同时承认SimpleNamespace且真实Request覆盖缺口结论正确，应作低重要度weight1的措辞/测试描述单元，不能等重于一般中危功能误报。
3. 对所有报告低重要度维护性事实使用相同合并上限。至少把E06 H13c/d/e/f按同一维护性观察族限额，或明确为何它们比E01四个契约更独立、更值得分母；不能只对某份报告合并“防灌水”。
4. 给D2每个unit增加 `family_id` 与归并规则，公开分母形成过程。事实是否错放D2，严重度过强/边界不足放D3，缺原始执行实物放D4。一个问题可跨维度体现不同缺陷，但不能同一个证据缺失重复化为多个事实错误。

仅将E08-F02权重3→1、F03权重2→1、保持现credit不变，D2就从13.529变为15.0（+1.471）。这只是展示分母敏感性，不是要求靠该数字指定新名次。E06四个H13正确单位合并成一个weight1，D2会从14.857变为14.375（-0.482）。即使小范围、可辩护的统一粒度都能改变近邻顺序。

### 4. 分数排序只能作为该评分设置下的账面顺序，不能据1—2分断言优劣

当前总分差：E06/E01约1.56，E02/E08约0.038，E04/E07约0.60，E03/E02约1.28。D3—D6的单个主观锚点就以0.5为增量；G08一个合理信用裁决变动2.34；D2粒度修订也能变动1分以上。小数位来自算式，不是测量精度。

**必须在最终结论中：** 将这些接近者写作“当前权重下分数接近，无法据此稳定区分”或同档展示；不要使用“显著高于”“明确第二/第五”之类强结论。不必编造统计置信区间，可公开至少两种合理争议项设置的敏感性表，列出哪些名次会互换。仅追加一句泛泛“不代表统计测量”不足以抵消主体中强名次断言。

## 应保留的裁决及边界

### G03 failed close恢复

G03的标题和独立事实一致：异常完成的close任务被缓存，TTL不重发RPC；确认browser/driver祖先释放后才清除记账。E05明确这个边界，给完整发现和事实信用合适。E06准确识别latch及异常/超时差异，**D1完整发现信用**可保留；它另写“一次异常必泄漏真实context”“进程重启前不会恢复”，D2仅部分正确也合适。这是发现机制与夸大后果分开，不矛盾。

必须一直保持：失败不代表真实context肯定存活；同进程BrowserService shutdown/startup在祖先确认成功后可恢复；需要重启整个Python进程不是所有context异常的必然结论；若driver.stop本身latched失败且祖先也无法确认，则有更强恢复限制。不要因为回收策略有意就把运维恢复缺口全判误报，也不要把保留所有权本身等同新泄漏。

E07仅指出后果、又“只能重启进程”过度，D1部分/D2部分合理。E03如果明确承诺异常close会TTL自动自愈，反证成立。G03不应为了弥补E08未发现而降低权重；E08缺少这一有效审查内容可以由D1自然体现。

### G06错误映射与G08挂起分开

E06确实指出容量拒绝与external close创建取消的500和Java泛化错误，应保留信用。新的watcher挂起会遮蔽部分HTTP响应，但不能倒过来否定没有结构化映射的代码事实。E08没具体发现该机制，不因它发现G08而自动获得G06；反之亦然。

### Optional[Request]建议

E08/E06的Optional改法均会破坏当前FastAPI路由注册；在D6扣建议安全性合理。原Request=None可正常注入，不能为了静态类型整洁把原代码列为真实功能缺陷。两份相同错误应同口径对待。

### 不要求把E08排第一

一个独有且重要的真实缺陷应得足额发现信用，也不能自动覆盖广度、其他事实错误和修复建议质量。E08 Java异常收敛/失败close恢复等覆盖不足可在D1/D5反映。公平目标是不同报告以相同粒度、相同证据规则计分，并诚实呈现名次敏感性，不是维护现有排序或强行奖励某个产品。
