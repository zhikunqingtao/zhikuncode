# 最终评分同侪审计：主张归属与事实扣分

审计范围：现行 `evaluation_data.json`、`scores_computed.json`、`normalize_families.py` 与冻结报告 E01–E08。仅检查错引、重复事实扣分、遗漏限定及分数依据是否匹配；不调整主观权重，不重新评分。以下三项已由主审明确采纳。

## 1. E01-F07：局部取消安全不能扩写成 watcher 全局有界保证

**精确出处**：[E01.md L283](../inputs/E01.md#L283)、[E01.md L284](../inputs/E01.md#L284)。

- L283 原文：“取消安全清理（`_finish_cleanup` 吞掉一次取消、保留中断状态后再抛）与‘失败关闭不缓存为成功’（`_close_resource` 的 `finished` 回调）体现了对 Playwright 语义的准确理解。”
- L284 原文：“断连检测 + `asyncio.wait` + 取消-汇合（`journey.py:39-57`）比‘依赖 ASGI 自动取消’更可靠；服务端截止时间与客户端 130s 超时的预算划分（120+5+5）有注释支撑。”

**审计意见**：这两句描述局部清理语义、设计评价及预算注释，并没有明确保证 watcher 必定有界退出。不能仅用另行发现的 watcher 无界汇合反例，把该报告没有识别的根因变成它已经提出的错误事实。

**主审已采纳口径**：E01-F07 由部分支持改为完整支持（credit = 1）。漏掉 watcher 根因只在 D1 发现维度反映，不再作为 D2 事实反证。

## 2. E02-F07：未识别具体根因不等于总时限观察错误

**精确出处**：[E02.md L135](../inputs/E02.md#L135)，原编号 P3-9。

L135 原文：“Python 清理阶段无总时限（`journey.py:50-57` 的 `gather` + `cleanup_timeout=5.0` 多资源串行），最坏可能超出 Java 130s 预算，得到 `PYTHON_CALL_FAILED`（资源仍由 TTL 兜底）”。建议为：“清理阶段加总时限（`asyncio.wait_for`）”。

**审计意见**：原文提出的是清理缺乏总时限、最坏可能超出客户端预算，并未声称已经解释 CancelScope 吞取消的特定根因。以“未识别 CancelScope、串行清理并非该根因”扣 D2，会把发现不足再次当作事实错误。同一句中的 TTL 恢复保证已经归入 E02-F06，不应在 F07 重复事实扣分。

**主审已采纳口径**：E02-F07 由部分支持改为完整支持（credit = 1）。未识别 watcher 根因只在 D1 反映；TTL 相关问题保留在既定事实族 F06 中。

## 3. E06-F07：改引真实总预算判断，保留其验证限制

**应排除的错引**：[E06.md L388](../inputs/E06.md#L388)，即提取项 A9。原文：“清理错误不掩盖主错误；取消安全（`_finish_cleanup` 屏蔽一次取消后重抛）”，并引用 `journey.py:74-85`、`browser_service.py:306-321` 及对应测试。

**应采用的精确出处**：[E06.md L586](../inputs/E06.md#L586)。原文：“**130s/125s 边界**：真实负载下 Python 是否总能在 Java 130s 内上报，静态分析成立但未动态压测。”

**审计意见**：L388 对 `_finish_cleanup` 的局部取消安全陈述不能被外层 watcher 汇合问题直接反证。若评价总时限保证，应引用 L586 真正涉及 130s/125s 的判断，同时完整保留“未动态压测”限定，不能说报告已动态证明该时限。

**主审已采纳口径**：E06-F07 维持部分支持（credit = 0.5），依据改为 L586 的真实总预算判断；明确 A9/L388 的局部清理安全成立，且报告已披露未动态压测。
